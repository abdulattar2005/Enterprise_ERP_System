## Enterprise ERP System

A modular-monolith Enterprise Resource Planning (ERP) backend built with Java 17 and Spring Boot 3.
It covers five business areas (HR, Inventory, Accounting, Sales, Reporting) behind one secured REST API,
with Docker, Kubernetes, CI/CD and monitoring files for running it in production.

Author: Abdulrahim Ramjan Attar (backend development internship, monthly task)
GitHub: https://github.com/abdulattar2005

### 1. Project overview

**Goal.** Build an enterprise-grade ERP back end where the business areas work together instead of
being separate apps. A sale reduces stock and creates an accounting entry. A purchase receipt increases stock
and creates an accounting entry. A payroll run creates an accounting entry. Everything is audited.

**Chosen scope: Option 2, "Standard ERP"** (all five modules with basic features), plus the enterprise
concerns from the task: security, audit trail, caching, monitoring, CI/CD and deployment files.

| Area | What it does |
|---|---|
| HR | Employees, attendance (check-in / check-out), payroll with progressive tax, performance reviews |
| Inventory | Products, stock tracking, suppliers, warehouses, purchase orders, low-stock report |
| Accounting | Chart of accounts, double-entry journal, trial balance, automatic postings from other modules |
| Sales | Customers, sales orders (draft, confirm, cancel) with stock deduction and invoicing |
| Reporting | Dashboard, sales summary, low-stock and trial-balance reports |
| Platform | JWT login, role-based access, audit log, error handling, caching, metrics, OpenAPI docs |

#### Implemented vs. reference material

Being clear about this matters for review.

| Item | Status |
|---|---|
| All five modules, security, audit, caching, validation, tests | Implemented in code |
| Dockerfile, docker-compose, Jenkinsfile, GitHub Actions | Provided, ready to use |
| Kubernetes manifests, Terraform, Prometheus alerts | Provided as a reference starting point, not applied to a real cluster |
| Redis, Kafka, Elasticsearch, multi-region, 99.95% SLA | Not implemented. Described as the scale-out roadmap in `docs/02-architecture.md` |
| Flyway migrations | Not implemented yet. Schema is generated by Hibernate (see limitations) |

### 2. Architecture in one picture

```
                      +----------------------------------------------+
   HTTP + JWT         |                  erp-api                     |
  ----------------->  |  Spring Boot app, config, OpenAPI, demo data |
                      +----------------------+-----------------------+
                                             |
        +----------+-----------+-------------+-----------+------------+
        |          |           |             |           |            |
     erp-hr   erp-inventory erp-sales   erp-accounting erp-reporting  |
        |          |           |             ^           |            |
        |          +-----<-----+             |           |            |
        |        (sales calls inventory)      |           |            |
        +---- events: payroll, sales invoiced, purchase received -----+
                                             |
                      +----------------------+-----------------------+
                      |                   erp-core                   |
                      | base entity, security, audit, errors, events |
                      +----------------------------------------------+
```

Modules are separate Maven modules, so the compiler stops one module from reaching into another that it
is not allowed to depend on. Accounting never depends on Sales, HR or Inventory: it only listens to events that
live in `erp-core`. Full detail: [docs/02-architecture.md](docs/02-architecture.md).

### 3. Setup instructions

#### Prerequisites

- JDK 17 or newer
- Maven 3.9+
- (optional) Docker and Docker Compose

#### Run locally (no database setup needed)

```bash
git clone https://github.com/abdulattar2005/erp-system.git
cd erp-system
mvn clean install
mvn -pl erp-api spring-boot:run
```

The app starts on http://localhost:8080 using an in-memory H2 database and the `dev` profile, which loads a
little sample data.

- Swagger UI: http://localhost:8080/swagger-ui.html
- Health: http://localhost:8080/actuator/health

#### Demo accounts (development only)

| Username | Password | Roles |
|---|---|---|
| admin | admin123 | ADMIN, MANAGER, USER |
| manager | manager123 | MANAGER, USER |
| user | user123 | USER |

#### Try it with curl

```bash
# 1. log in
TOKEN=$(curl -s -X POST localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin123"}' | python3 -c "import sys,json;print(json.load(sys.stdin)['accessToken'])")

# 2. dashboard
curl -s localhost:8080/api/reports/dashboard -H "Authorization: Bearer $TOKEN"

# 3. low-stock products
curl -s localhost:8080/api/inventory/products/low-stock -H "Authorization: Bearer $TOKEN"

# 4. run payroll for a month
curl -s -X POST localhost:8080/api/hr/payroll/2026-10/run -H "Authorization: Bearer $TOKEN"

# 5. the ledger after payroll
curl -s localhost:8080/api/accounting/trial-balance -H "Authorization: Bearer $TOKEN"
```

#### Run the production-like stack with Docker

```bash
cp .env.example .env        # then edit .env and set real secrets
docker compose up --build
```

This starts the app (profile `prod`), PostgreSQL, Prometheus (9090) and Grafana (3000).

### 5. Technical details (short version)

- **Double-entry bookkeeping.** Every journal entry must have at least two lines, each line is either a debit
  or a credit, and total debits must equal total credits, otherwise it is rejected.
- **Optimistic locking on stock.** Entities carry a `@Version`. Two people changing the same product at once
  cannot silently overwrite each other; the second gets HTTP 409.
- **All-or-nothing sales.** Confirming an order deducts stock, creates the invoice event and the ledger entry
  in one transaction. If any line has too little stock, nothing is changed.
- **Marginal-slab payroll tax.** Each tax band only applies to the part of the salary inside that band.
- **Cache.** Product reads use a Caffeine cache (5 minute expiry) that is cleared on every stock change.
- **Audit trail.** Every create, update and stock movement is written to `audit_logs` in its own transaction.

More: [docs/02-architecture.md](docs/02-architecture.md) and [docs/03-module-specifications.md](docs/03-module-specifications.md).

### 9. Known limitations

1. The schema is created by Hibernate (`ddl-auto=update`). A production system should use Flyway migrations.
2. Users are an in-memory demo store. A real deployment should use a database or an identity provider (OIDC).
3. No login rate limiting or account lockout yet.
4. The product cache is per instance. With several instances a stock change can leave another instance's
   cache stale for up to 5 minutes; a shared cache (Redis) would fix this.
5. Events are in-process. They give atomic consistency inside one instance but are not a message broker.
6. Tax bands are demo values, not a real country's tax law.
7. Terraform and Kubernetes files have not been applied to a real cloud account.

## 1. Business Requirements

### 1.1 Purpose

A mid-size company runs HR, stock, sales and accounting in separate spreadsheets or tools. Numbers disagree,
work is repeated, and nobody can see who changed what. This ERP puts the four areas on one data model so
that one business event updates everything it should, and reports come from one source of truth.

### 1.2 Users and roles

| Role | Typical person | Can do |
|---|---|---|
| ADMIN | System owner, finance lead | Everything: payroll, accounts, audit log, terminate employees |
| MANAGER | Department manager | Manage employees, attendance, reviews, products, purchase orders, customers, sales orders, reports |
| USER | Staff member | Read the product catalogue and low-stock list |

### 1.3 Functional requirements

#### HR
- FR-HR-1 Create, read, update employees; list with paging and department filter.
- FR-HR-2 Employees cannot share an email address.
- FR-HR-3 Terminate an employee without deleting history (ADMIN only).
- FR-HR-4 Record daily check-in and check-out; at most one record per employee per day; show hours worked.
- FR-HR-5 Run payroll for a month: gross pay, tax, net pay per active employee; running it twice must not duplicate.
- FR-HR-6 Record performance reviews with a 1 to 5 rating.

#### Inventory
- FR-INV-1 Manage products with SKU (unique), price, stock quantity, reorder level, warehouse and supplier.
- FR-INV-2 Stock can only change through audited adjustments; it can never go below zero.
- FR-INV-3 Report products at or below their reorder level.
- FR-INV-4 Manage suppliers and warehouses.
- FR-INV-5 Create purchase orders with several lines; receiving one increases stock for every line, once only.

#### Accounting
- FR-ACC-1 Maintain a chart of accounts (asset, liability, equity, revenue, expense).
- FR-ACC-2 Post journal entries; every entry must balance (debits equal credits).
- FR-ACC-3 Produce a trial balance that shows whether the ledger is balanced.
- FR-ACC-4 Create entries automatically for confirmed sales, received purchases and processed payroll.

#### Sales
- FR-SAL-1 Manage customers.
- FR-SAL-2 Create a sales order priced from current product prices (draft).
- FR-SAL-3 Confirm an order: deduct stock, invoice, post to ledger, all or nothing.
- FR-SAL-4 Cancel only draft orders.

#### Reporting
- FR-REP-1 Dashboard with headcount, product count, low-stock count, inventory value, order counts, revenue, ledger status.
- FR-REP-2 Sales summary including average confirmed order value.

#### Platform
- FR-PLT-1 Log in and receive a time-limited token.
- FR-PLT-2 Every state change is recorded in an audit log readable by ADMIN.
- FR-PLT-3 Clear, uniform error responses.

### 1.4 Non-functional requirements

| ID | Requirement | How it is addressed |
|---|---|---|
| NFR-1 Security | Authenticated access, least privilege, no secrets in code | JWT, roles, environment-based secrets |
| NFR-2 Integrity | No lost updates, no half-finished business actions | Transactions, optimistic locking |
| NFR-3 Traceability | Know who did what and follow a request through logs | Audit log, correlation id |
| NFR-4 Performance | Fast catalogue reads | Caffeine cache, paging, indexes on unique columns |
| NFR-5 Operability | Health checks, metrics, alerts | Actuator, Prometheus rules |
| NFR-6 Portability | Runs the same locally and in the cloud | Docker, 12-factor configuration |
| NFR-7 Maintainability | Clear boundaries, tests | Maven modules, layered code, test suite |

### 1.5 Assumptions and out of scope

- Single currency, single company, no tax law beyond demo bands.
- No front-end is included; the REST API and Swagger UI are the interface.
- Not included: multi-currency, fixed assets, leave management, returns/credit notes, e-invoicing.

### 1.6 Data used

Business data as listed in the task: employee records, inventory items, financial transactions, sales data.
Sample data is created by `DemoDataLoader` in the `dev` profile (3 employees, 4 products, 1 supplier,
1 warehouse, 1 customer).

## 2. Architecture

### 2.1 Style: modular monolith with clean layering

One deployable application, internally split into Maven modules with enforced dependency directions.
This was chosen over microservices because the modules share transactions (a sale must change stock and the
ledger atomically) and the team and load do not justify the operational cost of distributed systems.
The module boundaries are kept clean so a module could later be extracted into its own service.

#### Module dependencies

| Module | Depends on |
|---|---|
| erp-core | nothing in the project |
| erp-hr | core |
| erp-inventory | core |
| erp-accounting | core |
| erp-sales | core, inventory |
| erp-reporting | core, hr, inventory, sales, accounting (read-only) |
| erp-api | all modules; it is the only runnable artifact |

Dependencies only point downward, so there are no cycles. Maven refuses to build a cycle.

#### Layers inside a module

```
web (controllers)  ->  service (rules + transactions)  ->  repository (Spring Data JPA)  ->  database
        |                    |
   dto records          domain entities
```

### 2.2 Cross-module communication: domain events

Accounting must react to sales, purchases and payroll without depending on those modules.

```
SalesOrderService.confirm()   --publishes-->  SalesInvoicedEvent    --+
PurchaseOrderService.receive() --publishes--> PurchaseReceivedEvent --+--> LedgerEventListener (Accounting)
PayrollService.run()          --publishes-->  PayrollProcessedEvent --+       |
                                                                              v
                                                                     JournalService.postSystemEntry()
```

The event classes live in `erp-core`, so publisher and listener share only a tiny contract. Spring delivers them
synchronously inside the publisher's transaction. That gives one important guarantee: **a business action and
its ledger entry commit together or not at all.**

Automatic postings:

| Event | Debit | Credit |
|---|---|---|
| Sales invoiced | 1100 Accounts Receivable | 4000 Sales Revenue |
| Purchase received | 1200 Inventory | 2000 Accounts Payable |
| Payroll processed | 5100 Salaries Expense (gross) | 1000 Cash (net) and 2100 Taxes Payable (tax) |

### 2.3 Data model

```
employees 1---* attendance          suppliers 1---* products *---1 warehouses
employees 1---* payroll             suppliers 1---* purchase_orders 1---* purchase_order_lines *---1 products
employees 1---* performance_reviews customers 1---* sales_orders 1---* sales_order_lines (product_id, no FK)
accounts  1---* journal_lines *---1 journal_entries
audit_logs (stand-alone, append-only)
```

Notes:
- Every business table has `id`, `version` (optimistic lock), `created_at`, `updated_at` from `BaseEntity`.
- `sales_order_lines` stores `product_id`, product name and unit price as a snapshot, so old orders stay correct
  after a product is renamed or repriced, and Sales does not depend on Inventory's tables.
- Money columns are `NUMERIC(14,2)` mapped to `BigDecimal`.
- Unique constraints: employee email, product SKU, supplier name, warehouse code, account code,
  (employee, work date) in attendance, (employee, period) in payroll.

### 2.4 Algorithms and data structures

**Double-entry validation** (`JournalService.validateBalanced`): one pass over the lines; keeps two running
`BigDecimal` totals; rejects negative amounts, lines with both or neither side, fewer than two lines, and
unequal totals. Totals are compared with `compareTo`, not `equals`, so 100.0 equals 100.00. O(n).

**Trial balance**: one grouped SQL query (`sum(debit)`, `sum(credit)` per account) mapped straight into records,
instead of loading every line into memory.

**Marginal-slab tax** (`PayrollService.calculateTax`): an ordered list of bands (`Slab(upTo, rate)`). For each band,
tax the part of the salary between the previous limit and this band's limit, then move the lower bound up.
Example for a monthly gross of 100000 with bands 25000 at 5%, up to 75000 at 10%, above at 20%:
`25000*5% + 50000*10% + 25000*20% = 1250 + 5000 + 5000 = 11250.00`.

**Optimistic locking for stock** (`ProductService.adjustStock`): read product (with version), compute the new
quantity, reject if negative, `saveAndFlush`. If another transaction changed the row first, the update's
`WHERE version = ?` matches nothing and the database layer raises an optimistic-lock failure, which the API
maps to HTTP 409. No row locks are held while the user thinks, so reads stay fast.

**Caching** (`@Cacheable` / `@CacheEvict`): product lookups are cached by id in Caffeine (max 5000 entries,
5 minute expiry). Every stock change and product update evicts that id. Trade-off: eviction happens before the
transaction commits, so in a rare race another thread could re-cache the old value until it expires.

**Paging**: list endpoints take `page`, `size`, `sort` through Spring's `Pageable`.

### 2.5 Security architecture

```
client --Bearer JWT--> Spring Security filter chain
                         1. validate signature + expiry
                         2. map "roles" claim -> ROLE_* authorities
                         3. @PreAuthorize on controller method
                       --> controller --> service --> repository
```

Passwords are checked once at login against BCrypt hashes. After that the API is stateless: each request carries a
signed token. See `SECURITY.md`.

### 2.6 Observability

- **Logs**: every line includes `[correlationId]`. The id comes from the `X-Correlation-Id` request header or is
  generated, and is returned in the response header.
- **Metrics**: Actuator + Micrometer expose `/actuator/prometheus` (HTTP latency and counts, JVM, connection pool).
- **Health**: `/actuator/health/liveness` and `/readiness` for Kubernetes probes.
- **Alerts**: `monitoring/alerts.yml` (instance down, 5xx rate above 2%, p95 above 500 ms, DB pool waiting).

### 2.7 Deployment architecture (reference)

```
Internet -> Load balancer / Ingress (TLS) -> Service -> erp-system pods (2..6, autoscaled)
                                                             |
                                                  PostgreSQL (RDS, multi-AZ, encrypted)
Prometheus scrapes pods -> Grafana dashboards, alert rules
```

### 2.8 Design decisions and trade-offs

| Decision | Reason | Trade-off |
|---|---|---|
| Modular monolith | Shared transactions, simple operations | One deploy unit; scaling is all-or-nothing |
| Synchronous in-process events | Atomic business action + ledger entry | Not a message broker; no replay or cross-service delivery |
| Optimistic locking | High read concurrency, no lock waits | Clients may need to retry on 409 |
| DTO records at the API boundary | Hide internals, avoid lazy-loading problems | More small classes |
| Soft delete for employees | Keep payroll and audit history | Queries must consider status |
| Caffeine (local) cache | No extra infrastructure | Not shared between instances |
| H2 for dev, PostgreSQL for prod | Zero-setup local run | Small dialect differences; mitigated by H2 PostgreSQL mode and containerised Postgres option |

### 2.9 Scale-out roadmap (not implemented)

These come from the task's enterprise description and are the logical next steps:

1. Flyway migrations and `ddl-auto=validate`.
2. Redis as a shared L2 cache; keep Caffeine as L1.
3. Kafka (or the outbox pattern) to publish events to other systems and to extract modules into services.
4. PostgreSQL read replicas for reporting queries.
5. Elasticsearch for product and customer search.
6. OIDC identity provider replacing the demo user store.
7. Second region and tested failover for a 99.95% availability target.

## 3. Module Specifications

Each section lists entities, business rules, and the failure responses a client can expect.
Errors always use the body `{timestamp, status, error, message, details[]}`.

| Status | Meaning here |
|---|---|
| 400 | Validation failed or malformed JSON |
| 401 | Missing, expired or invalid token / wrong login |
| 403 | Logged in but role not allowed |
| 404 | Record not found |
| 409 | Concurrent change or uniqueness conflict; reload and retry |
| 422 | Business rule violated |

### 3.1 erp-core

| Piece | Behaviour |
|---|---|
| BaseEntity | id, version, createdAt, updatedAt |
| AuditService | Writes `audit_logs` in a new transaction; user is taken from the security context, or `system` |
| Security | `/api/auth/login` returns `{accessToken, tokenType, expiresInSeconds}`; `/api/auth/me` shows the caller |
| GlobalExceptionHandler | Maps exceptions to the statuses above; unexpected errors return a generic 500 and are logged |
| CorrelationIdFilter | Adds `X-Correlation-Id` to logs and responses |
| Events | `SalesInvoicedEvent`, `PurchaseReceivedEvent`, `PayrollProcessedEvent` |

### 3.2 erp-hr

**Employee**: first name, last name, unique email (stored lower-case), department, job title, monthly salary,
hire date (not in the future), status ACTIVE / ON_LEAVE / TERMINATED.

Rules
- Duplicate email on create or update: 422.
- Terminate sets status TERMINATED, keeps the record (ADMIN only).
- Only ACTIVE employees can check in.

**Attendance**: one row per employee per day. Check-in twice: 422. Check-out without check-in or twice: 422.
Hours worked = minutes between check-in and check-out divided by 60, two decimals.

**Payroll**: period `yyyy-MM`; anything else: 422.
- Runs for ACTIVE employees only; employees already paid for the period are skipped, so repeated runs are safe.
- Gross = monthly salary. Tax = marginal slabs (see architecture 2.4). Net = gross minus tax.
- When at least one new row is created, a `PayrollProcessedEvent` is published and a ledger entry is posted.
- ADMIN only.

**Performance review**: rating 1 to 5 (validated), free-text comments, reviewer = logged-in user.

### 3.3 erp-inventory

**Product**: unique SKU, name, category, unit price, stock quantity, reorder level, active flag, optional
warehouse and supplier. `lowStock` is true when stock is at or below the reorder level.

Rules
- Initial stock is set only at creation. Later changes go through `adjust-stock` (positive adds, negative removes).
- Adjustment of zero: 422. Result below zero: 422 (`Insufficient stock for SKU: available X, requested Y`).
- Concurrent adjustment of the same product: the second gets 409.
- Every adjustment is audited with its reason.
- Reads of a single product are cached and the cache entry is cleared on each change.

**Supplier**: unique name. **Warehouse**: unique code (stored upper-case).

**Purchase order**: supplier plus one or more lines (product, quantity at least 1, unit cost).
Status DRAFT then RECEIVED. Receiving
1. adds each line's quantity to the product's stock,
2. sets the status to RECEIVED,
3. publishes `PurchaseReceivedEvent` (ledger: inventory up, payables up).
Receiving a non-DRAFT order: 422.

### 3.4 erp-accounting

**Account**: unique code, name, type, active flag. Default chart created at start-up (idempotent):

| Code | Name | Type |
|---|---|---|
| 1000 | Cash | ASSET |
| 1100 | Accounts Receivable | ASSET |
| 1200 | Inventory | ASSET |
| 2000 | Accounts Payable | LIABILITY |
| 2100 | Taxes Payable | LIABILITY |
| 3000 | Owner's Equity | EQUITY |
| 4000 | Sales Revenue | REVENUE |
| 5000 | Cost of Goods Sold | EXPENSE |
| 5100 | Salaries Expense | EXPENSE |

**Journal entry**: date (defaults to today), description, reference, lines. Rules
- At least two lines; each line has exactly one of debit or credit, greater than zero; no negatives.
- Total debits equal total credits, otherwise 422.
- Unknown or inactive account: 404 or 422.
- Entries are append-only; there is no update or delete (corrections are made with a new reversing entry).

**Trial balance**: per account total debit and credit, grand totals, and `balanced` flag.

### 3.5 erp-sales

**Customer**: name, optional unique email, phone, company.

**Sales order**: customer plus lines (product, quantity at least 1). Created as DRAFT; unit prices are copied from
the product at that moment, line total = price times quantity, order total = sum of lines. Inactive products
cannot be ordered.

- Confirm (DRAFT only): deduct stock for every line, set CONFIRMED, publish `SalesInvoicedEvent`, ledger entry
  posted. If any line lacks stock, the whole transaction rolls back: no stock changes, order stays DRAFT, 422.
- Cancel (DRAFT only): set CANCELLED, no stock or ledger effect.
- CONFIRMED and CANCELLED orders are final.

### 3.6 erp-reporting

All endpoints are read-only and MANAGER or ADMIN.

| Report | Content |
|---|---|
| Dashboard | active employees, active products, low-stock count, inventory valuation (stock times price), draft and confirmed orders, confirmed revenue, ledger balanced |
| Sales summary | counts per status, confirmed revenue, average confirmed order value |
| Low stock | products at or below reorder level, lowest first |
| Trial balance | same as accounting |

## 4. API Reference

Base URL (local): `http://localhost:8080`. Interactive docs: `/swagger-ui.html`. Machine-readable: `/v3/api-docs`
(both disabled in the `prod` profile).

All endpoints except login, health and metrics need the header `Authorization: Bearer <token>`.
Lists accept `?page=0&size=20&sort=id,desc`.

### Authentication

| Method | Path | Role | Notes |

## 5. Deployment Guide

Three ways to run the system, from simplest to most production-like.

### 5.1 Local development (H2, profile `dev`)

Requirements: JDK 17+, Maven 3.9+.

```bash
mvn clean install
mvn -pl erp-api spring-boot:run
```

Open http://localhost:8080/swagger-ui.html. Data is in memory and resets on every restart.
Sample data is loaded by the `dev` profile only.

### 5.2 Docker Compose (PostgreSQL, profile `prod`)

```bash
cp .env.example .env          # edit all values; use long random secrets
docker compose up --build -d
docker compose ps
curl localhost:8080/actuator/health
```

| Service | Port | Purpose |
|---|---|---|
| app | 8080 | ERP API |
| db | internal | PostgreSQL 16 with a named volume |
| prometheus | 9090 | Metrics and alert rules |
| grafana | 3000 | Dashboards (the Prometheus datasource is pre-provisioned) |

In the `prod` profile the Swagger UI is switched off, and the app will not start without `ERP_JWT_SECRET` and
the other required variables. There is no demo data; log in with the passwords you set in `.env`.

Stop: `docker compose down` (add `-v` to delete the database volume).

### 5.3 Kubernetes (reference manifests)

Prerequisites: a cluster, `kubectl`, an image pushed to a registry (the Jenkins or GitHub pipeline does this),
and a PostgreSQL database reachable from the cluster.

```bash
kubectl apply -f kubernetes/namespace.yaml

# create the real secret (see kubernetes/secret.example.yaml for the keys)
kubectl -n erp create secret generic erp-secrets \
  --from-literal=DB_URL=jdbc:postgresql://<db-host>:5432/erp \
  --from-literal=DB_USERNAME=erp --from-literal=DB_PASSWORD='<password>' \
  --from-literal=ERP_JWT_SECRET='<32+ random chars>' \
  --from-literal=ERP_ADMIN_PASSWORD='<...>' --from-literal=ERP_MANAGER_PASSWORD='<...>' \
  --from-literal=ERP_USER_PASSWORD='<...>'

# edit the image name in kubernetes/deployment.yaml, then:
kubectl apply -f kubernetes/deployment.yaml -f kubernetes/service.yaml -f kubernetes/hpa.yaml
kubectl -n erp rollout status deployment/erp-system
kubectl -n erp port-forward svc/erp-system 8080:80
```

The manifests configure: 2 replicas, zero-downtime rolling updates, readiness and liveness probes,
CPU and memory requests and limits, non-root user, dropped capabilities, and an autoscaler (2 to 6 pods at 70% CPU).

Not included, add for production: an Ingress with TLS, a NetworkPolicy, a PodDisruptionBudget,
and a restriction so only Prometheus can reach `/actuator/prometheus`.

### 5.4 Infrastructure as code (Terraform reference)

`infrastructure/terraform` describes a VPC, an EKS cluster and a multi-AZ encrypted PostgreSQL instance on AWS.

```bash
cd infrastructure/terraform
terraform init
terraform plan -var 'db_password=<secret>'
```

Review the plan carefully before `terraform apply`: instance sizes, CIDR ranges and module versions are starting
values, and the files have not been applied to a real account. Do not commit state files or passwords.

### 5.5 CI/CD pipelines

| Pipeline | File | Stages |
|---|---|---|
| Jenkins | `ci-cd/Jenkinsfile` | Checkout, Build, Test (unit + integration and OWASP dependency scan in parallel), Build and push Docker image, Deploy to staging (main branch) |
| GitHub Actions | `.github/workflows/ci.yml` | Build and test on every push and pull request, then build the Docker image |

Jenkins needs a `docker-registry` credential, `kubectl` access to the staging cluster, and the registry name set in
the Jenkinsfile (`registry.example.com/erp` is a placeholder).

### 5.6 Release checklist

1. `mvn clean verify` passes.
2. CHANGELOG updated and version bumped.
3. Image built and pushed with a unique tag (the build number).
4. Secrets set in the target environment; no default passwords.
5. Deploy to staging, check `/actuator/health` and run the smoke test below.
6. Promote to production; watch error rate and latency for 15 minutes.

Smoke test:

```bash
TOKEN=$(curl -s -X POST $URL/api/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"..."}' | python3 -c "import sys,json;print(json.load(sys.stdin)['accessToken'])")
curl -s $URL/api/reports/dashboard -H "Authorization: Bearer $TOKEN"
```

### 5.7 Rollback

Kubernetes: `kubectl -n erp rollout undo deployment/erp-system`.
Docker Compose: redeploy the previous image tag. Database: because the schema is generated by Hibernate and
changes are additive, rolling back the app is normally safe; for destructive changes take a backup first.

## 6. Operations Manual

### 6.1 Health and monitoring

| What | Where |
|---|---|
| Liveness | `/actuator/health/liveness` (restart the pod if this fails) |
| Readiness | `/actuator/health/readiness` (remove from load balancing if this fails) |
| Metrics | `/actuator/prometheus` |
| Dashboards | Grafana, Prometheus datasource pre-provisioned |
| Alerts | `monitoring/alerts.yml` |

Useful queries:

| Question | PromQL |
|---|---|
| Requests per second | `sum(rate(http_server_requests_seconds_count[1m]))` |
| Error ratio | `sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) / sum(rate(http_server_requests_seconds_count[5m]))` |
| p95 latency | `histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket[5m])) by (le))` |
| DB connections in use | `hikaricp_connections_active` |
| JVM heap used | `jvm_memory_used_bytes{area="heap"}` |

Histogram buckets for latency are not enabled by default in Spring Boot. To use the p95 alert, add
`management.metrics.distribution.percentiles-histogram.http.server.requests: true` to `application.yml`.

### 6.2 Logs

Each line has a correlation id: `2026-10-27 10:15:30.123 INFO  [3f2c...] c.e.s.SalesOrderService - ...`.
To trace one request, take the `X-Correlation-Id` response header and search the logs for it.
Clients may send their own `X-Correlation-Id` (up to 64 characters).

### 6.3 Alert response (runbooks)

| Alert | Likely cause | First steps |
|---|---|---|
| ErpInstanceDown | Crash, bad deploy, DB unreachable | `kubectl -n erp get pods`, `kubectl -n erp logs <pod>`, check readiness, roll back if a deploy just happened |
| ErpHighErrorRate | Code bug, DB trouble, dependency failure | Look for 500 logs by correlation id, check DB health, roll back the last release if correlated |
| ErpSlowRequests | Slow queries, CPU saturation, pool exhaustion | Check CPU and DB pool panels, look for large unpaged queries, scale out |
| ErpDbPoolExhausted | Long transactions or too small a pool | Check slow queries; raise `DB_POOL_SIZE` only if the database has capacity |

### 6.4 Incident process

1. Detect: alert or user report. Note the time.
2. Assess: user impact, since when, which endpoints.
3. Mitigate first: roll back, scale out, or disable the failing feature. Fix root cause afterwards.
4. Communicate: tell affected users what is wrong and when the next update comes.
5. Review: write down timeline, root cause and prevention actions within a few days.

### 6.5 Routine tasks

| Frequency | Task |
|---|---|
| Daily | Check dashboards and alert history; confirm backups succeeded |
| Weekly | Review audit log for unusual activity (`GET /api/audit`); check dependency-scan results |
| Monthly | Run payroll (`POST /api/hr/payroll/{yyyy-MM}/run`); confirm trial balance is balanced; review low-stock report |
| Quarterly | Test a database restore; review user access; rotate secrets |

### 6.6 Backup and recovery

- Database: use automated daily backups with point-in-time recovery (the Terraform reference keeps 7 days).
- Test the restore quarterly; an untested backup is not a backup.
- Recovery steps: restore the database to a new instance, update `DB_URL` in the secret, restart the deployment,
  verify with the smoke test and the trial balance.
- Application is stateless and rebuilt from the container image.

### 6.7 Common problems

| Symptom | Cause | Fix |
|---|---|---|
| App fails on start: `jwt-secret must be set` | Missing or short `ERP_JWT_SECRET` | Set a value of 32+ characters |
| 401 on every call | Token expired or missing `Bearer ` prefix | Log in again |
| 403 | Role too low for the endpoint | Use a user with the required role |
| 409 on stock change | Two changes at once | Reload the product and retry |
| 422 `Insufficient stock` | Not enough quantity | Receive a purchase order or adjust stock |
| 422 `Entry is not balanced` | Debits differ from credits | Fix the amounts |
| Stock looks old on one instance | Local cache, up to 5 minutes | Wait, or adopt a shared cache (Redis) |

### 6.8 Capacity notes

Starting point from the manifests: 2 pods at 250m CPU and 512 MiB each, scaling to 6. These are untested
estimates; run a load test (for example with k6 or JMeter) against staging before relying on them.

## 8. Analysis Questions

Answers to the five questions in the task, using this project as the worked example.

### 1. What architectural patterns are most effective for enterprise systems?

There is no single best pattern; the right one depends on team size, load and how tightly the business
processes are connected. The patterns that pay off most often:

- **Layered architecture** (controller, service, repository) keeps HTTP, business rules and storage separate,
  so each can change and be tested alone. Used in every module here.
- **Modular monolith** gives clear boundaries with one deployment. It fits when business actions span
  modules and must be atomic, as a sale does here (stock, invoice, ledger). It is cheaper to run than
  microservices and can be split later.
- **Event-driven integration** decouples modules. Accounting reacts to events instead of being called by Sales,
  HR and Inventory. In this project the events are in-process; a broker such as Kafka is the next step.
- **Domain-driven design ideas**: each module owns its own concepts (an HR employee is not a Sales customer)
  and exposes a small API to the others.
- **Microservices** become worthwhile when teams need to deploy independently or parts must scale separately,
  but they bring distributed transactions, network failures and heavy operations. Start modular, split when
  there is a real reason.

### 2. How can modular design improve maintainability?

- **Enforced boundaries.** Separate Maven modules mean Accounting cannot import Sales classes: the build fails.
  The rules are checked by the compiler rather than by memory and code review.
- **Smaller blast radius.** A change inside HR cannot silently break Inventory, because HR is not visible to it.
- **Clear ownership and easier onboarding.** A new developer can understand one module in isolation.
- **Independent testing.** Module unit tests run without starting the whole app.
- **Replaceability.** Because modules talk through services and events, a module can later become its own service.
- **Cost:** more files and some up-front thought about where code belongs.

### 3. What security considerations are unique to enterprise applications?

- **Many roles and least privilege.** Different people may see different data (salaries are ADMIN or MANAGER only).
  Here every endpoint carries a `@PreAuthorize` rule.
- **Auditability.** Enterprises need to prove who changed what and when. The append-only audit log is written in its
  own transaction so it survives rollbacks.
- **Financial and personal data.** Money uses exact decimals, ledgers are append-only, and personal data brings
  privacy laws (see COMPLIANCE.md).
- **Integrity under concurrency.** Optimistic locking and transactions prevent lost updates and half-done actions.
- **Identity integration.** Real companies use single sign-on (OIDC, SAML). This project uses a demo user store and says so.
- **Secrets and supply chain.** Secrets come from the environment; dependency scanning runs in the pipeline.
- **Compliance.** Standards such as ISO 27001, GDPR and SOC 2 require processes as well as code.

### 4. How does caching strategy affect system performance?

Caching trades freshness and simplicity for speed.

- **Benefit.** Product lookups are read far more than written. A Caffeine cache answers from memory
  instead of the database, which lowers latency and database load.
- **Invalidation is the hard part.** Here every stock change evicts the product's entry, and entries expire after
  5 minutes as a safety net.
- **Known trade-offs in this project.** The cache is per instance, so with several pods another pod may serve a
  slightly old stock figure for up to 5 minutes. Eviction also happens just before commit, so a rare race can
  re-cache an old value. For stock-critical decisions the confirm-order path always re-reads the row inside the
  transaction and relies on the version check, not on the cache.
- **Scaling up.** A two-level design (local cache in front of a shared Redis) keeps speed while sharing state.
  Hit and miss ratios should be monitored; a cache that rarely hits is just overhead.
- **What not to cache.** Money balances and anything where being stale causes a wrong decision.

### 5. What monitoring is essential for production systems?

Cover the "golden signals" plus business health:

- **Availability**: health probes and an alert when an instance is down.
- **Latency**: p95 / p99 response time (alert above 500 ms in `alerts.yml`).
- **Traffic**: requests per second.
- **Errors**: 5xx ratio (alert above 2%).
- **Saturation**: CPU, memory, JVM heap, database connection pool (alert when requests wait for a connection).
- **Logs with correlation ids** to follow one request across the system.
- **Business checks**: for an ERP, the most valuable one is that the trial balance stays balanced; the dashboard
  exposes `ledgerBalanced` and it can be polled and alerted on.
- **Audit review** for suspicious behaviour, and **dependency scanning** for known vulnerabilities.
- Good alerts are few, actionable and tied to a runbook (see the operations manual).

## Security Policy

### Reporting a vulnerability

Do not open a public issue for a security problem. Email the maintainer (see the GitHub profile) with a
description, steps to reproduce and the affected version. You will get an acknowledgement and a fix plan.

### Supported versions

Only the latest release receives security fixes.

### Security controls in this project

| Area | Control | Where |
|---|---|---|
| Authentication | Login with username and password; passwords stored as BCrypt hashes; short-lived signed JWT (HS256, default 60 minutes) | `erp-core/.../security` |
| Authorization | Roles ADMIN, MANAGER, USER enforced with `@PreAuthorize` on every controller | each `web` package |
| Stateless API | No server session, CSRF disabled because no cookies are used | `SecurityConfig` |
| Input validation | Bean Validation on all request bodies; unreadable or invalid input returns 400 | `dto` records, `GlobalExceptionHandler` |
| Injection | Spring Data and JPQL with bound parameters only; no string-built queries | repositories |
| Error handling | Uniform error body; no stack traces or internal messages sent to clients | `GlobalExceptionHandler`, `application.yml` |
| Audit trail | Who did what, written in a separate transaction so it survives rollbacks | `AuditService` |
| Data integrity | Optimistic locking, unique constraints, database transactions | entities, services |
| Secrets | No secrets in source for production; `prod` profile requires environment variables | `application-prod.yml` |
| Container | Multi-stage build, non-root user, dropped Linux capabilities in Kubernetes | `Dockerfile`, `kubernetes/` |
| Dependencies | OWASP dependency-check stage in the Jenkins pipeline | `ci-cd/Jenkinsfile` |
| Transport | TLS must be terminated at the ingress / load balancer (see deployment guide) | deployment |
| Database | Terraform reference enables storage encryption, backups and private subnets | `infrastructure/` |

### Before going to production

These are known gaps. Close them before real use.

1. Replace the in-memory demo users with a database or OIDC identity provider.
2. Change every default password and generate a long random `ERP_JWT_SECRET`.
3. Add login rate limiting and lockout (for example at the API gateway).
4. Terminate TLS in front of the app and restrict `/actuator/prometheus` to the cluster network.
5. Add Flyway migrations and switch Hibernate to `validate`.
6. Add refresh tokens or token revocation if you need logout to invalidate tokens.
7. Rotate secrets on a schedule and store them in a secret manager.

## Compliance Notes

This project is **not certified** against any standard. This document shows how the design supports the
ideas behind ISO 27001, GDPR and SOC 2, and states honestly what is still missing. Certification needs
organisational processes (policies, training, audits) that software alone cannot provide.

### ISO 27001 (information security management)

| Control idea | Support in the project | Gap |
|---|---|---|
| Access control | Role-based access on every endpoint | No periodic access review process |
| Cryptography | BCrypt password hashes, signed tokens, encrypted DB storage in the Terraform reference | TLS must be configured at deployment |
| Logging and monitoring | Audit log, correlation ids, Prometheus metrics and alerts | No central log shipping configured |
| Secure development | Tests, code review checklist, dependency scanning in CI | No formal threat model |
| Backup | Daily automated backups in the Terraform reference (7 days) | Restore tests not scheduled |
| Supplier management | Supplier records exist as a business feature | Not an information-security supplier review |

### GDPR (personal data)

Personal data held: employee names, emails, salaries; customer names, emails, phone numbers; usernames in the audit log.

| Principle | Support | Gap |
|---|---|---|
| Lawfulness and purpose | Data is limited to what each business function needs | Legal basis must be documented by the operator |
| Data minimisation | Only required fields are stored | none known |
| Integrity and confidentiality | Roles, validation, audit trail | Field-level encryption not implemented |
| Accountability | Audit log of changes | No data-protection impact assessment |
| Right of access | Data can be read through the API by authorised staff | No self-service export |
| Right to erasure | Employees are soft-deleted (status TERMINATED) to keep payroll and accounting history | No anonymisation routine yet |
| Retention | Not automated | Define and implement retention rules |

### SOC 2 (trust service criteria)

| Criterion | Support | Gap |
|---|---|---|
| Security | See SECURITY.md | See "Before going to production" |
| Availability | Health probes, 2 replicas, autoscaler, multi-AZ database in the reference files | No tested failover or SLA measurement |
| Processing integrity | Double-entry validation, transactions, optimistic locking | none known |
| Confidentiality | Role separation, secrets from environment | Secret manager not wired in |
| Privacy | See GDPR table | See GDPR gaps |

### Service level targets

The task description mentions a 99.95% availability target and multi-region deployment. These are
**design targets for a full production rollout, not measured results**. The single-region reference
infrastructure here would need load testing, failover tests and a second region to support them.
